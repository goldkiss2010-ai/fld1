# 状態と観察を分ける

FLD1の目的は、生成側で求めた運動を制作環境で扱うことです。計算側の座標系で位置・速度・付随属性を保存し、制作側で補間・変換・投影・描画を行います。画面中心や解像度を粒子座標に含めません。

表示用にオブジェクトを回す操作では、保存された状態は変わりません。重力方向を変えて運動を変える操作は計算条件の変更です。視点操作とシミュレーション条件の変更は区別します。

## 速度を送る理由

位置だけの線形補間では、区間ごとの軌跡が直線になります。位置と保存する進行座標qに対する微分dx/dqがあれば、端点の位置と速度に一致する三次Hermite曲線を構成できます。

補間はサンプル間の再構成です。衝突や急な方向転換などを低頻度の保存で十分に表せるとは限りません。オーバーシュートもあり得ます。保存頻度は運動と許容誤差から決めます。

## 三つの時間間隔

数値計算の積分刻み、キャッシュ保存間隔、映像のフレーム間隔は別のものです。細かく計算しても毎ステップ保存する必要はありません。表示フレームを増やすだけでは、保存時に落とした運動は復元できません。

## 制作側の自由

カメラ、投影、点の大きさ、色、合成は表示側の機能です。FLD1自体が提供する描画機能ではありません。座標規約・時間・運動が揃った高密度キャッシュへ置き換えれば、低密度で決めた観察条件を適用できます。ただし粒子数が変わるので、個別インデックスに結びついた編集が引き継がれる保証はありません。

## DCCで扱いやすいローカル原点

FLD1 v1はオブジェクトのpivotやscene centerをメタデータとして持ちません。したがって、生成側の物理座標をそのまま保存するか、DCCで扱いやすいローカル座標へ平行移動してから保存するかはproducer側の設計事項です。

編集性を優先する場合は、キャッシュ全体で固定した中心 (C) を一度だけ決め、位置を `x_local = x - C` として保存すると扱いやすくなります。平行移動なので微分 `dx/dq` は変わりません。たとえば定義域が `[0, 2π)^3` の粒子場なら、`C=(π,π,π)` として書き出せば、DCC側ではpivotを原点 `(0,0,0)` に置いたまま自然に回転できます。

中心はフレームごとに再計算しません。各時刻のboundsや平均位置から中心を取り直すと、座標系そのものが時間変化し、オブジェクトが意図せず漂う原因になります。複数のFLD1へ一つの場を分割して書き出す場合も、各ファイルで別々に中心を求めず、同じ (C) を共有します。これにより、DCC側で複数キャッシュを重ねても一つのオブジェクトとして回転・移動できます。

これはv1のバイト規約ではなく、DCC handoff時の推奨ワークフローです。シミュレーション固有の座標原点を保存する必要がある場合は、その座標系をそのまま使って構いません。

## 範囲と制約

固定長の構造により、読み書きとフレームへの直接アクセスが単純になります。一方で、非圧縮の状態列なので大規模キャッシュでは容量と帯域が問題になります。

メッシュ接続、素材、ソルバー設定、分岐構造、座標メタデータは扱いません。まず粒子状態の受け渡しに範囲を絞り、拡張は互換性を考えて別途定義します。

## 時間への対応はDCC側が持つ

キャッシュは計算側の進行座標qに沿った状態を持ちます。新規の基本規約ではqを保存サンプル番号とし、sample_rate=1に固定します。旧キャッシュではqが生成側のシミュレーション秒などの場合もあります。映像の何秒でどこまで進めるかは、DCC側のq=g(t)が決めます。

保存する速度はdx/dqです。補間間隔もqの単位で揃えます。表示時間に対する速度が必要なら、dx/dt=(dx/dq)g'(t)で換算します。この関係を保てば、再生速度・停止・逆再生を計算側の運動から分離できます。

sample_rateという既存フィールド名は維持しますが、その意味を「qの単位あたりの保存サンプル数」とします。qの単位はヘッダーに保存されないので、生成側の説明に必須です。既存の秒基準キャッシュはqがシミュレーション秒の例であり、数値をそのままステップ基準と呼び替えません。
